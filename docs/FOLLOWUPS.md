# Follow-ups

Open items that are known but not scheduled.

- [ ] **CI: judge the `objects` cache trial.** The `linux` job in `.github/workflows/ci.yml` uses `github-cache-mode: objects`; `mac` and the package jobs still use the `target` payload, where Cargo rebuilds every workspace crate on every run because checkout resets file mtimes (about 8 minutes on mac, 5 on Linux). After a few runs on `main`, compare `linux`'s clippy and nextest build times, its `mbx[cache]` hit counts and its cache entry size (`gh cache list`) with runs from before the change. If it wins, move `mac`, `package-mac` and `package-linux` over; if not, delete the two inputs.
- [ ] **CI: raise the Actions cache limit.** One set of main's build caches was about 10.3 GB against the 10 GB repository limit (Settings > Actions > General; extra storage is billed), so GitHub evicts an entry each cycle and that job builds cold. Check which entries survive with `gh cache list`. Around 25 GB leaves room, and would also allow `save-on-pull-request` again for pull requests with several revisions.
- [ ] **CI: thin LTO in the package jobs.** `package-mac` and `package-linux` build the real release profile (thin LTO, one codegen unit), about 17 minutes on mac with a warm cache, the longest job in the merge queue. `CARGO_PROFILE_RELEASE_LTO=off` and `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16` in `ci.yml` only (`release.yml` keeps the profile) would shorten it, not measured. The cost: main's DMG and Linux artifacts would be slower builds than a release, and a break that only LTO shows would first appear at release time.
- [ ] **Release: check the split mac build on the next tag.** `release.yml` builds the arm64 and x86_64 slices in `build-mac-slice` and joins them in `build-mac` (`BUILD_ONLY` and `PREBUILT` in `build/darwin/package.sh`). Only the build-only path was dry-run; the join, sign and notarize path first runs on the next `vX.Y.Z` tag. Expect `build-mac` plus its slices to take 35 to 45 minutes, down from 64.
- [ ] **`fetch` in the TypeScript Worker.** The JavaScriptCore Worker (`crates/bundles/src/js.rs`) has no `fetch`, nor `Headers` / `Request` / `Response` / `Blob` or `crypto.subtle` (documented in `docs/bundles.md`). Adding it means a native that runs the request on `recur-http` and resolves a promise from the worker loop, plus those classes in the prelude. No shipped bundle needs it.
- [ ] **Vim on the editor model, not CodeMirror 5.** `crates/editor/src/vim/` is a port of `@replit/codemirror-vim`, which runs vim.js on a CodeMirror 5 adapter; `vim/cm.rs` ports that adapter. Motions, operators and ex commands work in CM5 (line, char) positions with deliberate out-of-range arithmetic (`ch = -1`, `INF`, a line past the end) that `cm.rs` clips into offsets; `CurOp` / `op_begin` / `op_end` mimic CM5's event batching, which `.` repeat and macro recording depend on; search cursors, scroll geometry and bookmarks are in the same terms. Rewriting vim onto `EditorState` offsets, `SelectionRange` and transactions would drop the adapter, but it is a rewrite of each motion and operator: build a much broader vim test suite first (only a handful of integration tests in `crates/editor/tests/view.rs` cover about 11.6k lines). Also: in replace mode (`R`) Backspace deletes instead of only moving left, because the editor keymap handles it before vim.
