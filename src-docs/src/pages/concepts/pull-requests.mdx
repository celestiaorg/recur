# Pull requests

Open **Pull requests** in the sidebar to see PRs across your projects. The list syncs from GitHub and includes PRs opened outside Recur, not just the ones Recur opened.

Recur talks to GitHub through the `gh` CLI, so it uses the account you have already authenticated with `gh auth login`.

## The dashboard

PRs are grouped into **Needs your attention**, **Workspace is responding**, **Open**, and **Merged**. A PR needs your attention when:

- your review was requested
- you were assigned
- changes were requested on your PR
- your checks are failing

Filter by project, by status (Open, Draft, Merged, Closed, All), or by review and check state. Sort by recently updated, newest, oldest, or title.

## Where a PR opens

A PR that has a workspace opens in that workspace: Recur selects the workspace and switches its center to the pull request view, with the chat on the left and the terminal below as usual. This is the same from the dashboard, the Inbox, a notification, the sidebar, the titlebar's **View PR**, the command palette and a link in the chat.

A PR without a workspace opens as a page of its own. So does an older or closed PR of a workspace that has a newer one. **Create workspace** in the page's titlebar checks the PR out into a task workspace and takes you there, on its pull request view.

## Reviewing

Open a PR to get its **Conversation**, **Commits**, **Files changed** (the full diff) and **Checks**. Leave line comments, then submit them together as a comment, an approval, or a request for changes. Reply to threads, resolve them, react, and mention people with autocomplete. Findings from reviewer agents show up alongside human comments.

The PR's title, state, people, attention labels and branch lead the page. In a workspace the Conversation tab is called **Overview** and leads with the state, the number, the title (hover it when it is cut short), the people and the attention labels. The branch is in the workspace's titlebar.

A PR without a workspace gets its own chat for Ask, Plan, and Review against the project checkout. New chats on a PR start in Review. Run `/review` there to have an agent review it.

## Acting on a PR

In a workspace, the PR's actions are where you work:

- The workspace titlebar has the PR's next step, whatever the center shows: **Ready for review** on a draft, **Fix checks** (starts an agent on the failing checks), **Queued**, **Conflicts** or **Blocked**, or **Merge** with a merge commit, squash, or rebase, limited to the methods the repository allows.
- **View PR #N** in the titlebar switches the center to the pull request. Its menu has **Open in GitHub** and **Convert to draft**.
- The workspace's own **Update with base**, **Pull updates**, **Push updates** and **Force push** bring the branch up to date and move commits between the workspace and GitHub.
- The right end of the pull request's tab row has **Send back** (hand the review to the workflow's conductor), the pending comments chip and **Approve** / **Request changes**, while the pull request view shows.

On the page of a PR without a workspace, the titlebar has all of them: **Create workspace**, **Open in GitHub**, the draft state, merge, update with base, and the review actions.

In a workspace chat, `/fix-checks` investigates failing checks, `/address-review` fixes or answers unresolved review comments, and `/update` brings the branch up to date with its base. `/open-pr` and `/open-draft-pr` open a PR with an agent-written title and summary.

## Automatic fixes

**Settings → Pull requests → Automatic fixes** has Recur run those actions for you. Each one is on until you turn it off:

- **Fix merge conflicts automatically** runs Update with base when a PR conflicts with its base. A clean merge or rebase just pushes; when git leaves conflicts, `/update` asks the agent to resolve them.
- **Fix failing checks automatically** runs `/fix-checks` when a PR's checks fail.
- **Address review comments automatically** runs `/address-review` when a PR has new review activity. It runs a turn only when a comment still needs a response.

They apply to your own open PRs that have a Recur workspace (not a workspace made from someone else's PR), and run in that workspace's chat, the same way you would. Recur checks after each PR sync (every few minutes, while it is open), and waits while the chat is busy. Only new problems count: a conflict, failing check or comment that was already there when Recur started, or when you turned the setting on, is left for you. A re-run that fails again counts as a new failure. Conflicts and checks stop after 3 tries in a row until the PR is clean again (checks pass, or the branch merges cleanly). Address review stops after 3 runs on a PR, until Recur restarts. The workspace's activity feed says what started each run.

`/address-review` reads only comments from people with write access to the repository and from review bots such as Copilot. It fixes what it agrees with, pushes, replies on each thread from your GitHub account, and resolves the threads it fixed. Disputed threads stay open for the reviewer.

## Settings

Each project's page has **Open PRs on GitHub**. When it is off, workflows open a Local PR inside Recur instead of a GitHub PR. Merge method, update method, commit message defaults, and **Conventional Commits** live under **Settings → Pull requests**, and each project can override them. The automatic fixes are there too.
